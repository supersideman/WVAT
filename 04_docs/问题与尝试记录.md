## 一、工具链与构建（Keil / ARMCC）

### 1.1 编译通过但下载报"找不到 .axf"

- **症状**：`Error: Flash Download failed - Could not load file '...\output\LCD.axf'`
- **定位**：先以为是下载器问题；翻 `output\LCD.build_log.htm` 才发现链接阶段失败，
  真实错误是 `L6218E: Undefined symbol lv_font_montserrat_44`。
- **根因**：`lv_conf.h` 里把 `LV_FONT_MONTSERRAT_44` 置 1 只是"允许编译"，
  **对应的 `lv_font_montserrat_44.c` 还必须被加进 Keil 工程的编译组**。
- **修复**：脚本自动把该文件插入 `.uvprojx` 的 Font 组。
- **教训**：`Target not created.` + 构建仅耗时 1 秒 = 编译或链接早就失败了，
  `Flash Download failed` 永远只是最后一个症状。**看到"找不到输出文件"，先往上翻日志找第一个 `Error:`**。
- **论文价值**：★★★★☆ 典型的"错误提示不是根因"案例。

### 1.2 中文注释导致宏"未声明"

- **症状**：编译报 `UI_C_PRESSED 未声明`、`UI_ICON_MIC 未声明`，
  但文件里明明有定义。
- **定位**：用 MSVC 单独编译同一份源码也能复现；检查字节发现文件里是 GBK 代码页，
  中文注释被按 GBK 解码后，**末尾字节恰好构成续行符 `\`**，把下一行 `#define` 吞进了注释。
- **根因**：源文件存为无 BOM 的 UTF-8，编译器按系统代码页（936/GBK）解析。
- **修复**：所有中文注释的源文件改为 **UTF-8 with BOM**。
- **教训**：这个坑在"编辑工具保存时剥掉 BOM"之后会**复发**，属于工程纪律问题。
- **论文价值**：★★★★★ 建议写入"跨编码环境的工程实践"一节。

### 1.3 `Get-ChildItem -Include` 静默不生效

- **症状**：写了个"给所有源文件补 BOM"的循环，运行后什么都没打印，
  编译依旧报 1.2 的错误。
- **根因**：PowerShell 的 `Get-ChildItem -Include` 在不配合 `-Recurse`
  或通配符路径时**匹配不到任何文件**，而且**不报错**。
- **修复**：改用 `Where-Object { $_.Extension -in '.c','.h' }`。
- **教训**：**"脚本跑了但没做事"比"脚本报错"危险得多**，脚本要打印处理数量自证。
- **论文价值**：★★★☆☆ 可作为"自动化脚本要自证"的例子。

### 1.4 .cmd 批处理双击一闪就退

- **症状**：双击 `start_gateway.cmd`，窗口闪一下就消失，报
  `'le' is not recognized as an internal or external command`。
- **根因**：文件用 **LF 换行**写入，而 `cmd.exe` 只认 **CRLF**，
  整份脚本被拆错行（`title` 被截成 `tit` + `le`）。
- **修复**：改 CRLF + 纯 ASCII 内容。
- **论文价值**：★★☆☆☆

## 二、LVGL 图形界面

### 2.1 勾/叉图标只画出一笔

- **症状**：成功回执里的对勾只显示一条斜线。
- **根因**：多个图标函数共用同一组 `static lv_point_t` 数组，
  后面的 `lv_line` 对象引用的是同一块内存，内容被后来者覆盖。
- **修复**：每个图标函数使用自己独立的 static 数组。
- **论文价值**：★★★★☆ 静态缓存在 GUI 框架里的别名问题，很典型。

### 2.2 小尺寸下描边图形不可辨识

- **症状**："下一首"图标实际显示成两根细线；"音量"的喇叭看起来像大于号。
- **根因**：LVGL 8.2 **没有填充多边形/三角形图元**，用 `lv_line` 画轮廓时，
  在 28px 尺寸下只剩两三根细线，形状感丢失。
- **修复**：改用**多个实心矩形按"台阶"堆叠**近似三角形（喇叭锥体、播放三角）。
- **论文价值**：★★★★★ 这是"资源受限 GUI 下的图元近似"问题，很适合写进设计章节。

### 2.3 `lv_obj_remove_style_all()` 清掉了坐标

- **症状**：锁屏与主界面本应上下叠放（y=0 / y=280），实际复位后**直接看到主界面**；
  从抽屉返回时**黑屏**。
- **定位**：串口打印几何信息，得到 `stage: x=0 y=0 w=0 h=0`、`set_y=-280 (readback=0)`。
- **根因**：LVGL 8 里 **`lv_obj_set_pos/set_size` 写的其实是"样式属性"**，
  而子控件的 `lv_obj_remove_style_all()` 会把刚设好的坐标一并清除，
  于是两个层都回到 (0,0)：主界面盖住锁屏（现象一）；切页时整体上移 280px，
  两层一起被推出屏幕外（现象二）。
- **修复**：改为 **先 build 内容、再 set_pos**；并在 `ui_stage.h` 注释里写明原因。
- **教训**：**一个根因可以同时解释两个看似无关的现象**——遇到"多个 bug 同时出现"，
  优先找共同原因。
- **论文价值**：★★★★★ 强烈建议写入。

### 2.4 调试打印的尺寸恒为 0，差点误导排查

- **症状**：上述调试输出里 `w=0 h=0`。
- **根因**：`lv_obj_get_width/get_y` 读的是**布局计算后的坐标**，
  初始化阶段尚未执行布局，读到的是 0。
- **修复**：打印前调用 `lv_obj_update_layout()`。
- **教训**：**假数据比没数据更危险**。第一版日志差点把结论引向"尺寸没设上"。
- **论文价值**：★★★☆☆

## 三、通信与协议

### 3.1 能发不能收：CubeMX 没使能串口中断

- **症状**：手表点击后网关能收到指令并回执，但手表屏幕的回执**永远停在初始状态**。
- **定位**：查 `.ioc` 与生成代码，`HAL_UART_Receive_IT()` 有调用，
  但工程里**既没有 `USART1_IRQHandler`，也没有 `HAL_NVIC_EnableIRQ(USART1_IRQn)`**。
- **修复**：在 `user_link.c` 内自行补充中断入口与 NVIC 使能
  （不修改 CubeMX 生成文件，避免下次重新生成被覆盖）。
- **论文价值**：★★★★☆ "生成代码未必完整"的实例。

### 3.2 设备复位后，前几条指令被静默丢弃

- **症状**：每次重新烧录/复位后，点前几个功能块"看起来成功"（有回执、有绿点），
  但**系统毫无动作**。
- **定位**：网关日志出现 `[去重] REQ_ID=1 已处理过，直接回缓存`。
- **根因**：手表复位后 `REQ_ID` 从 1 重新计数，而网关的去重表里还留着
  上一轮会话的 1..N，于是把**全新请求**误判为重传，只回缓存、不执行。
- **修复**：两处判定"设备已复位"即清空去重表——
  `REQ_ID` 回退，或心跳超时。并明确记录取舍（REQ_ID 是 uint8，255→1 回绕时
  会多清一次，代价仅为极小概率重复执行一次动作）。
- **论文价值**：★★★★★ 这是"幂等去重"设计的真实边界条件，很适合写进协议设计章节。

### 3.3 串口号会变 + CH340 有设备却无 COM 口

- **症状**：网关报 `could not open port 'COM6'`；后来发现口号已变成 COM13。
  另有一次 USB 枚举里能看到 `VID_1A86&PID_7523`，但系统没有生成任何 COM 口。
- **修复**：拔插一次即恢复；启动器改为**自动枚举 CH340**，不再依赖手抄口号。
- **教训**：**口号不写死**，由程序按 VID 查找。
- **论文价值**：★★★☆☆

## 四、PC 端动作执行（Windows）

这是本项目**代价最大**的一节，值得完整写入论文的"问题与解决"。

### 4.1 所有"按键类动作"从第一天起就是假的

- **症状**：日志显示 `[执行] A04 音量+ ok`，但系统音量不变；
  播放/暂停、下一首同样无效。而**锁屏、关显示器却一直正常**。
- **定位过程（四步，逐步排除）**：
  1. 确认不是演练模式（日志打印的是 `[执行]` 而非 `[演练]`）。
  2. 确认不是窗口站/会话问题（前后台进程都是 `WinSta0\Default`、Session 1）。
  3. 用 **CoreAudio 当尺子**客观测量：发送前 43.0% → 发送 5 次音量+ → 仍是 43.0%，
     证明"返回值成功 ≠ 动作生效"。
  4. 检查结构体尺寸：`sizeof(INPUT) = 32`，**而 x64 下必须是 40**。
- **根因**：`INPUT` 的 union 只写了键盘成员，**漏掉鼠标与硬件键成员**。
  `SendInput` 在 `cbSize` 不匹配时**不抛异常，只返回 0**，而旧代码把返回值丢弃了
  → 完全静默失败。
- **修复**：补全 union 三成员；并增加两道防呆：
  ```python
  if ctypes.sizeof(_INPUT) != 40:
      raise RuntimeError("INPUT 结构体大小异常，按键注入必失败")
  if user32.SendInput(2, inputs, size) != 2:
      raise RuntimeError("SendInput 未插入完整事件")
  ```
- **论文价值**：★★★★★ **最推荐写入的一条**。它同时说明了两件事：
  (a) 调用 Win32 API 时结构体布局必须精确；(b) **必须校验返回值**，
  否则"失败"会被误当作"成功"，形成系统性的假验证。

### 4.2 同一个调用，前台有效、后台无效

- **症状**：修好结构体后，用前台终端跑同一函数可以把音量推到 100%；
  但由工具链后台启动的网关进程调用时，仍然毫无效果。
- **定位**：用 CoreAudio 复测（43.0% → 43.0%）确认后台进程确实无效；
  再排除窗口站、会话、结构体三个因素。
- **根因**：**进程所处的运行环境没有输入注入权限**（受限令牌/沙箱），
  `SendInput` 返回"已插入事件"但事件到不了交互桌面。
- **修复**：**网关必须由用户在自己登录的桌面启动**（提供 `start_gateway.cmd`
  一键启动）。这也正是实际部署形态。
- **论文价值**：★★★★★ 说明"桌面自动化类程序对运行上下文的依赖"，
  以及为什么交付物要设计成"用户侧启动"。

### 4.3 音量改用 CoreAudio（可回读、可验证）

- **背景**：鉴于 4.1/4.2，音量不再走按键，改为直接调用系统音量接口。
- **实现**：`audio_win.py`，纯 ctypes 走 COM：
  `IMMDeviceEnumerator → GetDefaultAudioEndpoint → IAudioEndpointVolume`，
  调用 `SetMasterVolumeLevelScalar / GetMasterVolumeLevelScalar / SetMute`。
- **收益**：① 不受输入注入限制；② **可以把真实音量读回来**，
  回执变成"音量已调高 63%"而不是空话；③ 为后续"手表显示音量"提供数据源。
- **踩坑**：`CLSID_MMDeviceEnumerator` 一开始记错，`CoCreateInstance`
  返回 `0x80040154 REGDB_E_CLASSNOTREG`；正确值为
  `BCDE0395-E52F-467C-8E3D-C4579291692E`。
- **论文价值**：★★★★★ 建议作为"可验证性设计"的正例。

### 4.4 失败的尝试：`WM_APPCOMMAND` 与 SMTC 媒体会话

按时间顺序记录两次未采用的方案，答辩时被问到"为什么不用 X"可以直接回答。

**尝试 A：`WM_APPCOMMAND` 广播**
- 音量控制**有效**（早期"音量突然最大"就是它做的），
  但对**媒体键（播放/暂停、下一首）无效**。
- 结论：不可作为媒体控制的通用方案。

**尝试 B：Windows SMTC 媒体会话**
- 思路：直接调用系统媒体会话接口，绕过按键。
- 实现：PowerShell 5.1 + WinRT（需 `Add-Type -AssemblyName System.Runtime.WindowsRuntime`
  并手工桥接异步操作），Python 侧需 `winsdk`。
- 实测：**系统里查不到任何媒体会话**（即便网易云正在播放），
  `GetSessions()` 返回空 → 无法定位到可控对象。
- 结论：该机器上不可用，放弃。
- **论文价值**：★★★★☆ **"试过并说明为何放弃"是加分项**，
  比只说"实现了"更能体现工程判断。

### 4.5 测试工具本身出错，差点得出错误结论

- **症状**：自建的按键测试脚本里 `SendInput` 返回 `0/2`，
  一度判断"`SendInput` 完全不可用"。
- **根因**：测试脚本**自己重新定义了 `INPUT` 结构体**，同样漏了成员，
  `sizeof` 只有 32。**测试工具坏了**，不是被测代码坏了。
- **修复**：测试脚本改为直接调用生产实现 `intents._press_vk()`。
- **教训**：**验证工具本身也需要被验证**；否则会基于假证据做出错误的技术决策。
- **论文价值**：★★★★★ 极好的"实验方法学"素材。

## 五、工程与仓库

### 5.1 脚本误提交整个工作区

- **症状**：一次 `git add . tools` 误把上千个无关文件加入暂存区
  （1130 个文件 / 55 万行插入）。
- **修复**：`git reset --soft HEAD~1` + 重新精确 add；
  并把大量无关路径写入 `.gitignore`。
- **教训**：**永远不要在含大量无关文件的工作区根目录执行 `git add .`**；
  项目应放在独立子目录并且只在该目录内操作 git。

### 5.2 PowerShell `Set-Content` 把中文文档写成乱码

- **症状**：修好的 `STATUS.md` 突然无法被读取（报"非法 UTF-8"）。
- **根因**：PowerShell 5.1 的 `Set-Content` 默认用 **ANSI（GBK）** 编码写文本，
  把原本的 UTF-8 中文变成了无效字节序列，部分字符还被替换成 `?`。
- **修复**：写文本统一用
  `[System.IO.File]::WriteAllText($path, $text, (New-Object System.Text.UTF8Encoding($false)))`。
- **论文价值**：★★★☆☆

### 5.3 目录搬迁后，工作区内反而不能写

- **症状**：把 Keil 工程从桌面移入项目目录后，脚本往工程里复制源码被拒绝
  （`Access ... is denied`），尽管路径位于工作区内。
- **定位**：先用权限诊断脚本检查，结论为"权限本身正常"（当前用户拥有完全控制权、
  无异常权限项）→ 说明不是文件权限问题，而是**新搬入的目录没有继承沙箱授权**。
- **修复**：把该目录**复制**到工作区内新建路径（复制出的新文件会继承目标目录权限），
  校验文件数/体积一致后再删除旧目录。
- **论文价值**：★★☆☆☆ 属于环境工程细节，可放附录。

## 六、语音识别（Vosk 本地 ASR）

### 6.1 模型加载报"does not contain model files"，但模型完好

- **症状**：`vosk.Model(dir)` 抛异常 `Folder '...' does not contain model files`，
  可目录里 `am/final.mdl`、`graph/*.fst` 全在，字节数也对。
- **定位**：把同一份模型复制到 `C:\vosk-model-cn`（纯英文路径）→ 立刻加载成功；
  换回项目路径（含用户名「李思颉」）→ 必然失败。
- **根因**：`vosk` 底层是 C++（Kaldi），Windows 上用**窄字符**打开文件。
  路径里的非 ASCII 字符（本项目在 `C:\Users\李思颉\...` 下）被按 ANSI 解释，
  于是"文件确实存在，但按那个字节串找不到"。
- **修复**：模型固定放纯 ASCII 目录 `C:\Users\Public\vosk-model-cn`；
  `asr.py` 里按 `VOSK_MODEL_DIR` 环境变量 → ASCII 目录 → 项目目录 的顺序探测，
  并**主动拒绝非 ASCII 路径**（启动自检会直接说清楚）。
- **教训**：**给 C/C++ 库传路径前先确认它是不是窄字符**。Python 侧一切正常，
  不代表底层库能处理 Unicode。

### 6.2 语音识别静默失败：启动器把中文用户名写成 `???`

- **症状**：网关启动后语音一律失败，报 `No module named '_cffi_backend'`；
  但同一台机器、同一个解释器，命令行手动跑却完全正常。
- **定位**：查看 `start_gateway.cmd` 内容，发现硬编码的
  `C:\Users\李思颉\.dsh\...` 变成了 `C:\Users\???\.dsh\...`——
  因为该 `.cmd` 以 **ASCII 编码**写入，中文用户名无法表示，写的时候就被替换掉了。
  路径不存在 → 启动器 `if not exist` 回退到 `set PY=python` →
  命中 PATH 里的 **Python 3.15**，而 `cffi` 的扩展是 **cp312** 编译的 →
  解释器根本不去找 `_cffi_backend.cp312-win_amd64.pyd` → 报"模块不存在"。
- **修复**：启动器改为 PowerShell（`start_gateway.ps1`，UTF-8 **带 BOM**），
  `.cmd` 只剩三行薄壳。PowerShell 原生 Unicode，路径用 `$env:USERPROFILE`
  运行时拼接；并在启动时**硬校验 `sys.version_info == (3,12)`**。
- **教训**：
  ① **不要往 ASCII 批处理里写非 ASCII 路径**，用运行时展开；
  ② **启动时必须校验解释器版本**，否则 ABI 不匹配会伪装成"缺模块"；
  ③ 排查这类问题要**对比"我这边"和"用户那边"的实际解释器**，别看代码一样就下结论。

### 6.3 假识别兜底把故障伪装成"能用"

- **症状**：录音页按下录音键，"识别"立刻返回预设句子（下一首 / 我困了 / …），
  看起来流程全通，其实一次真识别都没发生。
- **定位**：网关在"打开麦克风失败"时把 `self.asr = None`，
  之后所有请求都走假识别；而假识别只是**循环返回 5 句预设文本**。
- **修复**：**彻底删除假识别**。现在任何一步失败都回 `ERR` 并打印真实异常，
  启动时先做依赖自检（cffi / 录音设备 / 引擎 / 模型），问题在启动阶段就暴露。
- **教训**：**"看起来在跑"比"跑不起来"更危险**。演示兜底数据必须显式标注，
  否则调试时会沿着错误的方向找很久（本项目在这条上浪费了两轮实机验证）。

### 6.4 1bpp 中文字库：三种典型错误

- **① 码表用绝对码**：LVGL 的稀疏表查找是
  `rcp = letter - range_start` 后再二分 `unicode_list`，
  即列表里必须是**相对码**，且 `range_length` 要覆盖整个区间。
  写成绝对码 + `range_length = 0` 的结果是**每个字都查不到**，整段文字空白。
- **② 位图按行补齐**：LVGL 的 1bpp 位图是**连续比特流**（`bit_ofs = y*box_w + x`），
  行末不补齐。按字节对齐打包会让每个字错位成"点阵雪花"。
- **③ 描述符越界**：`bitmap_index` 是 20 位、`adv_w` 是 12 位（1/16 px），
  大字号 + 大字符集时要检查是否溢出。
- **修复**：写 `gen_cn_font.py` 从系统字体生成，并配 `verify_font.py`
  **在 PC 上按 LVGL 的取位规则把字形画出来预检**——
  这一步把"改字库 → 烧板子 → 发现还是不对"的循环从 3 次降到 0 次。

## 七、C 语言与工程组织

### 7.1 include guard 与布局常量重名，整个头文件被静默跳过

- **症状**：`ui_main.c` 调用 `ui_status_visible()` / `ui_status_show_result()` 时，
  ARMCC 只给 `#223-D: function ... declared implicitly` 的**警告**，功能照常能跑，
  所以从写出来那天起一直没人注意。
- **定位**：换 MSVC 做交叉自检时出现 `C4013: "ui_status_visible" 未定义`；
  把预处理结果 (`cl /E`) 倒出来搜，发现 `ui_status_visible` **只在调用处出现一次**，
  声明根本没进来。再看宏定义：

  ```
  ui_theme.h   L61:  #define UI_STATUS_H      44      ← 布局常量：顶部状态区高度
  ui_status.h  L15:  #ifndef UI_STATUS_H            ← include guard，撞名了
  ```

  `ui_main.c` 先 `#include "ui_theme.h"`（把 `UI_STATUS_H` 定义成 44），
  再 `#include "ui_status.h"` 时 `#ifndef` 判断为假 → **整个头文件被跳过**。
- **根因**：同一个宏名被赋予两种含义（长度常量 / 包含保护）。
  谁先包含谁生效，是个**顺序敏感**的隐性依赖。
- **修复**：guard 改名 `UI_STATUS_PAGE_H`，并写脚本**全量比对**
  "所有头文件的 guard" vs "`ui_theme.h` 的全部 `#define`"——只此一处冲突。
- **教训**：
  ① **头文件 guard 应该带 `_H_` 或 `_INCLUDED` 后缀之外的独特前缀**，
     不要和"业务常量"共用命名空间（C 语言里宏是全局平铺的）；
  ② **警告不等于没问题**：`declared implicitly` 在老编译器里是警告，
     在 C99+ 标准里其实是错误；它往往意味着"你以为包含了的头其实没包含"；
  ③ **多编译器交叉自检很值**：ARMCC 放过的问题，MSVC 会报出来。
  值得写进论文（软件工程/代码质量部分）。

### 7.2 手工编辑留下的"孤立右括号"引发语法错误

- **症状**：Keil 报 `user_link.c(225): error: #169: expected a declaration`，
  但同一份文件在几分钟前还是好的。
- **定位**：用脚本移动一个函数时，只删了函数体，**漏删了结尾的 `}`**；
  编译器把那个孤立的 `}` 当成"函数外的声明"，于是报 `expected a declaration`。
- **修复**：删掉残留的括号；并把"只编译改动文件"的习惯升级为
  **改动后对全部固件源文件做一次全量编译自检**（9~10 个文件，几秒钟）。
- **教训**：**局部编译会漏掉"文件级残骸"**（括号、多余的 `extern`、重复定义）。
  这类错误往往在真正的编译（全量）时才暴露，早发现能省一次烧板子的往返。
