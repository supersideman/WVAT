# 手表 → AI → 做事：链路设计与协议规范

> 2026-10-19 · 硬件 OV-Watch（F411CEU6 + KT6368A）· 配套 [功能需求与方案](毕设-功能需求与方案.md)
> 本文是"阶段 0"的施工图：协议先定死，UI 与网关才好并行开发。

## 一、总体架构（三层，一句话说清）

```
   ┌──────────────┐   BLE-SPP 透传    ┌─────────────────┐   HTTPS    ┌──────────────┐
   │  OV-Watch    │  COM 口 / ASCII   │  PC 网关(Python) │ ─────────> │ DeepSeek API │
   │  F411+LVGL   │ ──"我要干什么"──> │  意图→动作执行    │ <───────── │              │
   │              │ <──"干完了/结果"── │                 │            └──────────────┘
   └──────────────┘                   └─────────────────┘
        显示 + 采集                        决策 + 执行
```

**每层职责，必须划清**（答辩会问）：

| 层 | 负责 | 不负责 |
|---|---|---|
| 手表端 | 采集用户意图、显示状态、超时/重传 | 不理解语义、不联网、不调 API |
| PC 网关 | 意图解析、白名单决策、执行动作、回传结果 | 不碰界面渲染 |
| 云端 LLM | 把"自然语言/模糊意图"映射成**结构化动作** | **绝不直接执行任何东西** |

## 二、协议规范（在作者 `OV+` 风格上扩展）

现有协议是 ASCII 文本行、`\r\n` 结尾、实现在 `user_MessageSendTask.c`。你新增 4 条：

| 方向 | 帧 | 含义 |
|---|---|---|
| 手表→PC | `OV+AI=<REQ_ID>,<CODE>[,<ARG>]` | 发起意图请求 |
| PC→手表 | `OV+AR=<REQ_ID>,<STATUS>,<TEXT>` | 应答（配对用 REQ_ID） |
| PC→手表 | `OV+EV=<EVENT>,<TEXT>` | 异步事件（如"音乐已暂停"） |
| 双向 | `OV+PING` / `OV+PONG` | 心跳保活（20s 一次） |

字段定义：

- **REQ_ID**：`0–255` 循环。用途是**配对请求与应答 + 去重**（重传同 ID 只执行一次）
- **CODE**：意图枚举码（见第四节），手表端只需发码，**不需要打字**
- **ARG**：可选参数，UTF-8
- **STATUS**：`OK` / `ERR` / `BUSY`
- **TEXT**：UTF-8，**≤ 60 字节**（见下方"屏显约束"）

示例：

```
手表: OV+AI=17,A03
网关: OV+AR=17,OK,已锁屏并静音
手表: OV+AI=18,T,帮我看看明天的天气
网关: OV+AR=18,OK,明天小雨 12~18℃
```

### ⚠️ 三个真正的坑（现在就写进设计，别等调试才发现）

1. **屏显约束反过来约束 LLM 输出**：240×280 的屏，一行中文约 8–10 字、显示 3 行就到顶。所以**必须要求 LLM 直接输出 ≤20 字的结果摘要**，而不是把长回复截断（截断读起来是断句，很难看）。这一条要写进 prompt。
2. **中文编码**：现有协议是纯 ASCII，加了中文载荷后必须**全程按字节处理**，长度按 `len(bytes)` 算，不能按字符数。同时确认 `user_MessageSendTask.c` 的收发缓冲够不够（建议 ≥128B），不够要改。
3. **`OV+` 前缀解析**：作者原实现用字符串比较，加入变长参数后要改成"前缀匹配 + 逗号切分"，否则 `OV+AI` 会误命中其他分支。

## 三、PC 网关设计（Python）

```
main
 ├─ serial_reader 线程 ──> queue.Queue（按 \r\n 切行、解码、去重窗口）
 ├─ dispatcher 线程   ──> 查 CODE 表 → 本地动作 或 LLM 解析 → 执行 → 回写
 └─ heartbeat 定时器   ──> 发 OV+PING，超时 3 次判定掉线 → 自动重连 COM
```

实现要点，按"会踩的先后"排：

1. **串口读取别用 `readline()` 裸读**：蓝牙 SPP 会粘包/半包。正确做法是 `read(in_wait)` 进缓冲区，自己按 `\r\n` 切。
2. **读线程与执行必须解耦**：LLM 调用要 1–3 秒，阻塞读线程就会丢掉手表的重传帧。用 `queue.Queue` + 独立 worker。
3. **去重窗口**：PC 侧缓存最近 10 个 `REQ_ID`，收到重复 ID 直接回缓存结果——这是**重传不重复执行的关键**。
4. **COM 掉线自动重连**：蓝牙掉线是常态，`serial.SerialException` 要捕获并每 2s 重试重开。答辩现场就靠这个保住演示。
5. **动作白名单**：LLM 只输出 `{"action": "LOCK_SCREEN", "args": {...}}` 这种 JSON，Python 侧只认白名单里的 action。**绝不让 LLM 生成 shell 命令**——危险，且演示一旦失败救不回来。
6. **API**：DeepSeek 是 OpenAI 兼容接口，`base_url=https://api.deepseek.com`，`model=deepseek-chat`。用 prompt 约束输出 JSON，解析失败就降级到规则。

## 四、动作白名单（这就是"做事"的具体清单）

| CODE | 意图 | 手表侧入口 | PC 侧执行 |
|---|---|---|---|
| `A01` | 放首歌 | 按钮 | 发送媒体键 `playpause`（pyautogui） |
| `A02` | 下一首 | 按钮 | 媒体键 `nexttrack` |
| `A03` | 我困了 | 按钮 | 锁屏（`LockWorkStation`）+ 静音 + 关显示器 |
| `A04` | 音量加/减 | 按钮 ×2 | 媒体键 `volumeup/down` |
| `A05` | 打开资料 | 按钮 | 打开指定文件夹/网页 |
| `A06` | 现在几点/状态 | 按钮 | 返回本地时间、电量（不调 LLM） |
| `T` | 自由指令 | 文本页 | **调 LLM** → 意图码 → 走白名单执行 |

**关键可靠性设计（这条最重要）**：

> `A01–A06` 这些**固定意图码走本地规则，完全不依赖网络和 LLM**。
> 只有 `T`（自由文本）才调云端。

这样做的收益：**断网、没额度、API 挂了，你的核心演示照样能跑**。LLM 是"增强"，不是"命门"。这一条同时回答了答辩必问的"如果断网怎么办"。

## 九、关于"联网"的澄清（答辩必问，先背下来）

**问：这套方案要手表联网吗？**
**答：不需要。手表物理上也做不到。**

三层理由：

1. **硬件上没有联网能力**：板子没有 WiFi 芯片，F411 上也没有跑 TCP/IP 协议栈；只有 KT6368A 这颗**蓝牙透传**模块。
2. **蓝牙不是"上网"**：蓝牙是点到点短距链路，最多把数据送到"配对的那台设备"，出不了局域网。真正访问 DeepSeek 的 HTTPS 请求是**在 PC 上发出的**。
3. **类比讲给老师听最省事**：**手表是遥控器，电脑是电视。遥控器从来不上网。**

所以"谁需要联网"要分清：

| 环节 | 需要什么 | 需要网络吗 |
|---|---|---|
| 手表发意图（`A01`–`A06`） | 蓝牙连到 PC | ❌ 不需要 |
| PC 执行固定动作（锁屏/放歌/音量） | 本地 Python | ❌ **不需要** |
| 自由文本（`T`）→ LLM 理解 | PC 的 WiFi / 网线 | ✅ 需要 |
| 手表本身 | 什么都不需要 | ❌ **永远不需要** |

**真正的限制不是网络，是距离**：蓝牙是近距离链路（一般 10m 级，穿墙会明显变差）。也就是说——

> **手表必须在电脑附近（同一个房间）才能用。**

演示场景完全没问题（手表和笔记本就在一张桌子上）。但如果你的设想是"人在外面，用手表指挥家里的电脑"，**现有硬件做不到**。论文里要老实写"本系统面向近距离交互场景"，这句话写出来是加分项，藏着不说才是隐患。

**想随身远程？** 那就得给板子加 WiFi 模块 + 跑 TCP/IP + TLS——128KB RAM 里塞这些非常紧，而且原板没留 WiFi 接口，需要飞线改板。**明确不建议**，答辩时作为"未来工作"讲一句即可。

## 十、语音输入链路（时间充裕后升级为主线）

前提变了：现在是**大四上提前做**、约 6 个月，所以语音可以从"可选"升成**主线卖点**。但底座要换成 **FryPi / F411 核心板**——因为（引脚实证）I2S2 的 `PB12(WS)/PB13(CK)/PB15(SD)` 三根全空闲且已引出，而 OV-Watch 板没有空闲 IO。

### 硬件接线（三根信号线）

```
INMP441 / ICS-43434 数字麦          FryPi 排针
  VDD  ──────────────────────────  3V3
  GND  ──────────────────────────  GND
  L/R  ──────────────────────────  GND（接地=左声道输出）
  WS   ──────────────────────────  PB12   (I2S2_WS / LRCLK)
  SCK  ──────────────────────────  PB13   (I2S2_CK / BCLK)
  SD   ──────────────────────────  PB15   (I2S2_SD / 数据输入)
```
- F411 做 **I2S 主机**，麦克风做从机
- 板上 **25MHz HSE** 让 I2S 时钟精度达标（这是 OV-Watch 没有的优势，那里只有 HSI）

### 采样与传输

| 参数 | 建议值 | 理由 |
|---|---|---|
| 采样率 | **16kHz**，单声道，16bit | 语音识别够用；32KB/s，USB 串口随便跑 |
| 采集方式 | **DMA 双缓冲**（半传输/全传输中断） | 不占 CPU，避免丢样 |
| 传输 | **USB 串口**（板载 CH340N） | 比蓝牙快两个数量级，音频流才传得动 |
| 触发 | 按键按下开始 / 再按结束 | 最稳；VAD 自动断句作为加分项 |

⚠️ 想走蓝牙传音频就得压缩（ADPCM 减半到 8KB/s），仍然很挤——**这条路上 USB 串口是明显更优解**。

### ★ 必须澄清的一点：DeepSeek 不做语音识别

> **DeepSeek 的 API 是文本大模型（`deepseek-chat` / `deepseek-reasoner`），不含语音识别（ASR），也不含语音合成（TTS）。**

所以语音链路是**两个模型接力**，别混为一谈：

```
麦克风 → PCM → PC →【ASR：语音转文字】→ 文本 →【LLM：文字转动作】→ 动作 → 回传
                     ↑ 这一环不是 DeepSeek            ↑ 这一环才是 DeepSeek
```

ASR 的可行选择（价格/额度需自行核实，我不给数字）：

| 方案 | 优点 | 代价 |
|---|---|---|
| **whisper.cpp 本地跑** | 免费、离线、隐私好、不怕断网 | 要占几十 MB 磁盘/内存，首次配置花时间；小模型中文准确率一般 |
| 云厂商 ASR（阿里/腾讯/讯飞等） | 准确率高、有免费额度 | 要注册+网络；免费额度用完要钱 |
| 浏览器/系统自带识别 | 零成本 | 国内不稳定，不建议用于答辩 |

**建议组合**：`whisper.cpp 本地` 做主力（答辩不依赖外网），云 ASR 作为对比实验——这正好凑成论文里"两种 ASR 方案的识别率与延迟对比"一节数据。

### 端到端时延预算（论文里要有这张表）

| 环节 | 估计耗时 |
|---|---|
| 录音（说完一句） | 2–4s（用户决定） |
| USB 传输 | < 0.1s |
| ASR（本地小模型） | 1–2s |
| LLM 推理 | 1–3s |
| 回传 + 屏显 | < 0.2s |
| **合计** | **约 4–9s** |

→ 所以手表端必须做**四段状态机**：`录音中 → 识别中 → 思考中 → 执行中`。这个状态机本身就是可写进论文的技术点，因为它决定了"用户觉得系统卡不卡"。

### 语音意图的两种用法

1. **指令式（稳）**：说"锁屏""放首歌""下一首"→ 端侧直接关键词匹配，**不经过 ASR 也不经过 LLM**，延迟 < 1s
2. **自由式（亮点）**：说"我有点困了"→ ASR → LLM → 映射到 `A03` 锁屏 + 静音

> 两种都要做：指令式保底（断网可用、演示不翻车），自由式出彩（答辩的"AI 感"）。

### 风险

- **麦克风拾音质量**：板卡周围有 USB/开关电源噪声，麦要尽量远离电源走线；必要时加简单软件高通滤波
- **中文识别准确率**：环境嘈杂时明显下降 → 论文里要写清测试条件（安静/嘈杂两档）
- **ASR 与 LLM 双重超时**：任一环节超时都要能降级到"指令式"或直接回"没听清，请再说一次"

## 十一、能不能接入 DSH？（能，但要分清接哪一层）

### 实证：DSH 有一次性非交互执行模式

跑 `dsh --help` 得到的官方示例里明确写着：

```
dsh headless "run the tests"      answer one task, print the result, and exit
```

也就是说，PC 网关只要一行子进程调用，就能把任务丢给 DSH 并拿到结果：

```python
subprocess.run(["dsh", "headless", "把桌面上的截图整理到 images 文件夹"],
               capture_output=True, text=True, timeout=120)
```

**技术上零难度。** 于是问题就从"能不能"变成"该不该"。

### 另一个实证（对你 ASR 选型更有用）

DSH 里打包了这些包（从 asar 清单读到）：

- `dsh-experimental-api-speech-to-text`
- `dsh-experimental-speech-to-text-sensevoice`
- `dsh-experimental-speech-to-text`
- `dsh-experimental-client-ui-voice-input`

底层是 **sherpa-onnx**（`onnxruntime.dll` + `sherpa-onnx-c-api.dll` + `.node` 绑定，已在 `sherpa-onnx-win-x64` 里解包），模型走 **SenseVoice**：
`sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`，int8 版约 **239MB**，从 HuggingFace 下载。

**这条对你的直接价值**：本地中文 ASR 的最优选型是 **sherpa-onnx + SenseVoice**，中英日韩粤多语、离线、中文准确率比 whisper 小模型明显好。你不必另装 whisper.cpp。

> ⚠️ 说明：这些是 `experimental` 包，我只确认了**包和动态库存在**，**没有验证界面里是否已启用、模型是否已下载**。要用先自己确认。

### 三条接法，差别在"哪些算你的"

| 方案 | 做法 | 毕设风险 | 建议 |
|---|---|---|---|
| **A 借技术栈，不借产品** | 自己写 Python 网关 + sherpa-onnx/SenseVoice 做 ASR + DeepSeek 做意图 | ✅ 低：ASR/意图/调度全是自己写 | **主线** |
| **B 白名单 + 转交 DSH** | 固定指令走本地白名单；**白名单覆盖不到时才** `dsh headless "..."` | 🟡 中：要写清"转交"边界 | **加分项** |
| **C 把手表当 DSH 的输入设备** | 语音直接喂给 DSH，让 DSH 全权执行 | ❌ **高**：核心能力全在别人的产品里，"你做了什么"无法回答 | **只当演示彩蛋** |

### 推荐架构：双通道意图路由（这个能写进论文）

```
         ┌── 快通道：白名单命中 ──> 本地执行（毫秒级、断网可用、结果确定）
语音意图 ─┤
         └── 慢通道：白名单未命中 ─> 转交 agent（秒级、能力上限高、结果不确定）
```

这条路由本身就是**技术贡献**：你能画架构图、测两条通道的时延分布、算命中率、论证"为什么不能所有请求都走慢通道"。而且它对答"如果断网怎么办""如果 AI 理解错了怎么办"都是天然答案。

### ⚠️ 安全红线（说重一点）

`dsh headless` 会让 agent 获得**真实的工具权限**（跑命令、改文件）。**语音识错一句话就可能造成不可逆破坏。**

所以转交必须加三道闸：
1. **只在白名单未命中时触发**，不要默认全走 agent
2. **手表屏幕二次确认**：屏显"要执行『xxx』吗？"，KEY1 确认 / KEY2 取消
3. **限定工作范围**：演示只放开某个测试文件夹，别放开桌面和全盘

### 答辩话术（如果真用了）

> "语音识别采用开源的 SenseVoice 模型做本地推理；**意图解析、动作白名单调度、通信协议、降级与确认机制均为自行设计与实现**；对于白名单之外的开放任务，系统提供可选的 agent 转交通道作为能力扩展。"

这段话诚实、划清了边界，而且**用开源模型不是减分项**——关键是别把别人的产品说成自己的。

## 十二、本地执行要不要"本地部署 AI"？（不需要，但要把四个东西分清）

**结论：快通道不是 AI，是查表。** 白名单命中的固定指令走的是 `if 关键词 → 动作`，**不需要任何模型、不需要联网、不需要显卡**。

容易混的是这四样东西，它们的"部署量级"差三个数量级：

| 组件 | 干什么 | 是不是"部署 AI" | 量级 | 快通道要不要 |
|---|---|---|---|---|
| **规则/白名单** | 关键词 → 动作码查表 | ❌ 完全不是 AI | 0 | ✅ **本体就是它** |
| **ASR 小模型** | 语音 → 文字 | 🟡 算，但很轻 | 约 239MB（SenseVoice int8），CPU 可跑 | 🟡 只在"用嘴说"时才需要 |
| **LLM 大模型** | 模糊语义 → 结构化动作 | ✅ 是，很重 | 几 GB 起，要显卡 | ❌ **不需要** |
| **TTS** | 文字 → 播报 | 🟡 算，但系统自带 | Windows SAPI，零部署 | ✅ 用它做反馈 |

**所以"本地部署 AI"这个说法要拆开看：**

- 说"我要本地部署大模型" → **不需要，也别做**。本科毕设没必要，几 GB 的 7B 模型质量和云端差一截，调试起来还麻烦
- 说"我要本地跑一个语音识别模型" → **可选，但很值**（见下）

### 三档方案，按"断网还能用什么"选

| 档位 | 本地有什么 | 断网时能做到 | 代价 |
|---|---|---|---|
| **① 零本地模型（最省事）** | 只有规则 + 系统 TTS | 图标按钮指令、关键词匹配（按按钮触发）**全可用**；语音识别不可用 | 零部署 |
| **② 本地 ASR（推荐）** | + SenseVoice/sherpa-onnx（约 239MB） | **语音也能用**（自由说话→本地识别→本地规则命中） | 下模型、配环境；CPU 推理 1–2s |
| **③ 本地 LLM（不建议）** | + 7B 级模型 | 连"模糊意图"都能离线 | 几 GB、慢、效果打折、与毕设无关 |

**我的建议：走 ②。** 理由：

1. 本地只放**ASR**，不放 LLM——这是性价比最高的分工
2. 意图理解继续走**云端 DeepSeek**（质量好、有额度、答辩有网就行）
3. 反馈播报用 **Windows 自带 SAPI**（`pyttsx3` 或 PowerShell 的 `System.Speech`），零部署
4. 这样断网时：**语音仍能识别 → 命中本地白名单 → 照常执行**，只有"我有点困了"这种模糊意图会失效

> 这一档正好对应论文里的**"离线降级能力"**实验：断网后 L1 指令可用率可以做到接近 100%，这是很硬的加分数据。

⚠️ 下载提醒：SenseVoice 模型在 HuggingFace 上，国内直连可能慢或失败，需要镜像源（自己查可用镜像，我没有验证过具体哪个可通）。

**一句话记住**：真正的智能在云端，可靠的本地在查表。**别指望笔记本跑大模型，指望它跑得快、跑得稳、断网不倒。**

## 十三、交互容错：确认机制怎么设计

### 第一件事：断网处理别"一刀切"

"断网就直接返回网络未连接"——**方向对（别搞复杂降级），但会误伤**。因为要分清哪一段真的需要网：

| 环节 | 需要网络吗 | 断网时 |
|---|---|---|
| 本地 ASR（SenseVoice） | ❌ | 照常识别 |
| **快通道：白名单命中** | ❌ | **照常执行** |
| 慢通道：LLM 意图理解 / 转交 agent | ✅ | 这才是要返回"网络未连接"的地方 |

所以正确的一句话是：**"断网时快通道照常工作，只有需要 AI 理解的复杂指令会提示网络未连接。"**

这不是"降级策略"，而是**结构上本来就这样**——白名单是本地代码，跟网络无关。这句话在答辩时比"我做了断网降级"更硬。

### 第二件事：先显示识别文本再发送——这个想法很好，但要分级

**你这个设计很对**，它把风险掐在最早一层：**在动作执行前就拦住"听错了"**。而且它能变成论文里一组很漂亮的对比数据（引入确认后误执行率从 X% 降到 Y%，代价是时延 +1.2s）。

但**一刀切会让它和你的核心场景打架**：

> 你的定位是"人边干别的事、不看屏幕" —— 那每一步都要求看屏幕确认，就把这个场景废掉了。

**建议做成三级**：

| 动作级别 | 例子 | 处理方式 |
|---|---|---|
| **A 安全动作** | 放歌/暂停/音量/锁屏/查时间天气 | **直接执行**，屏上只显示执行结果（不打断） |
| **B 破坏性动作** | 关程序/整理文件/删除/转交 agent | **必须先显示文本 + 二次确认** |
| **C 低置信度** | 没命中白名单、识别文本异常短或乱 | **强制走确认**；用户重录一次 |

**置信度怎么判（不需要模型给分）**：用"**是否命中白名单**"当代理指标就够了——
命中 = 高置信 → 直接执行；未命中 = 低置信 → 走确认或慢通道。这样实现简单，也不用去挖模型输出的 token 分数。

### 落地细节（手表只有 2 个按键 + 触摸）

- **显示**：一句中文 10–15 字，分 2 行、大字号；超长截断加"…"，别滚动（抬手看 1 秒，滚动画不动）
- **按键**：`KEY1 = 确认发送`、`KEY2 = 重录`；触摸也可以点屏上两个按钮（可选）
- **重录**：按 KEY2 直接覆盖上一次录音，**不退回首页**（少一次操作）
- **超时**：确认界面停留超过 5–8 秒无操作就自动取消并回首页，避免"卡在确认页"

### 一个更好用的折中：自动确认 + 可中断

如果想兼顾流畅和安全，可以这样：

```
识别出"锁屏" → 屏显"将执行：锁屏" + 1 秒倒计时 → 倒计时结束自动发送
                                     ↑ 这 1 秒内按 KEY2 可拦截
```

**好处**：用户不用每次按确认（不打断"边干别的"），但**看到的瞬间可以反悔**。对 A 级动作特别合适，演示时也显得很"聪明"。

### 落到论文里，这是一节很好写的内容

> "人机协同的容错设计：通过在意图确认环节引入分级确认与可中断自动确认机制，在不显著增加交互负担的前提下，将误执行率从 X% 降至 Y%。"

配上两张图（流程图）+ 一组数据（不同确认策略下的误执行率与时延），就是完整的一节。

## 十四、执行完给不给反馈：给，而且这是刚需

**答案是"必须给"，但手表端的硬件只留了一条通道。**

### 先看硬件能给你什么

| 反馈通道 | OV-Watch 现状 | 说明 |
|---|---|---|
| **屏幕** | ✅ 有（240×280） | **唯一可靠的手表端通道** |
| **喇叭** | ❌ 无 | BSP 无音频驱动 |
| **振动马达** | ❌ 无 | BSP 无马达驱动，硬件文档也没提 |
| LED | ⚠️ 有但没用 | Back 板 LED2–LED5 由 `LED_EN` 驱动，**在贴手那面，戴着看不见** |

所以用 OV-Watch 板，反馈只剩"屏幕"一条——而你自己的定位是"**边干别的事、不看屏幕**"，这两件事直接冲突。

### ★ 想做触觉反馈，就得走 FryPi 路线

加一个硬币振动马达只要：**1 个 GPIO + 1 个三极管 + 续流二极管**，几块钱的事。

- OV-Watch：**空闲 IO ≤5 个且没引出** → 加不了
- **FryPi：PA1–PA7 等一大批空闲且已引出** → 太容易了

> 也就是说：**"语音要麦"和"反馈要振动"这两个需求，指向同一个答案——FryPi。** 这不是巧合，可穿戴设备的输入和输出本来就需要额外引脚。

### 五段式反馈（屏 + 声 + 振动）

| 阶段 | 屏幕 | PC 声音 | 振动编码（若加马达） |
|---|---|---|---|
| 按下开始 | 🎤 录音中 | 短"嘀" | 短振 ×1 |
| 识别完成 | 显示识别文本 | — | 短振 ×2 |
| 已发送 | 思考中… | — | — |
| **成功** | 已锁屏 | TTS："已锁屏" | **长振 ×1** |
| **失败** | 网络未连接 | TTS："网络未连接" | **双短振**（错误码） |

**振动编码是关键**：戴着表、手在干别的、眼睛不看屏的时候，**节奏是唯一能传达"成了/没成"的方式**——跟手机通知的习惯一致。

### 但反馈不是越多越好

| 情况 | 该给的反馈 | 不该做的 |
|---|---|---|
| A 级安全动作成功 | 屏显示结果 + 一声短提示（**仅此**） | 每次都 TTS 念一遍，会烦 |
| B 级破坏性动作 | 执行前确认 + 执行后明确回执（屏 + 声） | 静默执行 |
| 失败 | **强提醒**：屏显原因 + 错误振动 + TTS | 只闪一下屏就没了 |
| 可配置 | "安静模式"只振动不出声 | 一刀切 |

### 论文角度：这也是一节

> "多模态反馈设计：在无扬声器、无振动马达的受限终端上，通过'屏幕 + 网关侧语音播报 + 外接触觉马达'三层反馈，使用户在非视觉使用场景下对任务完成状态的确知率从 X% 提升到 Y%。"

能测的指标：**察觉成功率**（做完后问"你知道刚才成了吗"）、**反馈延迟**、**误以为成功但实际失败的次数**。这组数据比"我做了个界面"有分量得多。

## 十五、那就只做屏幕反馈：定调 + 具体设计

**这个取舍是对的。** 理由三条：

1. **答辩是"看"的场景**，评委看的就是屏幕，屏幕反馈就是最直接的得分点
2. 振动马达属于**后期形态阶段**的东西，不影响你现在验证链路
3. 论文里可以老实写"受限终端的反馈局限 + 后续改进方向"，这是诚实，也是加分

所以定调：**现在只做屏幕反馈，触觉反馈写进"未来工作"。**

### 四段状态：用颜色 + 图标 + 6 个字，别用长句

240×280 的屏，投影出去会糊。**关键信息必须够大够粗**：

| 状态 | 颜色 | 图标 | 文案（≤6 字） | 停留 |
|---|---|---|---|---|
| 录音中 | 红 | 🎤 闪烁红点 | 正在录音 | 持续 |
| 识别中 | 黄 | 转圈/波形 | 识别中… | 持续 |
| 思考中 | 蓝 | 三点动画 | 处理中… | 持续 |
| **成功** | 绿 | ✓ | 已锁屏 | 1.5s 后淡出回主界面 |
| **失败** | 红 | ✕ | 网络未连接 | **3s，且必须手动关掉** |

**失败一定要比成功停留更久**——这是反馈设计的基本规矩，评委也会注意到这种细节。

### 240×280 的布局建议

```
┌────────────────────┐
│  ● 状态条（图标+词）  │  ← 顶部 40px，色块底
├────────────────────┤
│                    │
│   识别文本 / 结果    │  ← 中部主区，大字号 2–3 行
│   （最多 12 字）     │
│                    │
├────────────────────┤
│ KEY1 确认  KEY2 重录 │  ← 底部 36px 操作提示
└────────────────────┘
```

- 字号优先，宁可少显示几个字也别缩小
- 图标用 **LVGL 内置符号字体**（`LV_SYMBOL_OK` / `LV_SYMBOL_CLOSE` / `LV_SYMBOL_AUDIO` 等），**零 Flash 开销**——你 APP 只剩不到 50KB，别贴图

### 演示增强三招（这才是"能看见"的关键）

1. **★ PC 端镜像一个状态窗口**：网关本来就收到了所有状态，顺手开个小窗口显示"和手表一模一样的状态"。答辩时投影电脑，评委看得一清二楚。
   - 成本极低（Python 十行 UI），**演示效果翻倍**
   - 万一手表屏幕反光/太小，还有兜底
2. **把息屏逻辑临时关掉**：演示前把翻腕唤醒/超时息屏调到 30s 以上，别讲到一半黑屏
3. **加一个"最近一次执行结果"常驻小部件**：主界面留一行，显示上次做了什么。演示时可以反复回看，不用重演

### 一个零成本的"拟物反馈"小技巧

`LCD_BLK` 是 **PWM 控制背光**的（BSP 里有 `LCD_BLK` 这个网络）。所以你可以：

> **执行成功时让背光快速闪一下（比如 100ms 亮 → 100ms 暗 → 恢复）**，失败时闪两下。

这不是振动，但它是**屏幕之外的一点点物理感**，而且零成本、零额外引脚。演示时评委能感到"设备确实有反应"，比纯文字更活泼。

写论文时这也算一条"受限条件下的替代反馈手段"，很有意思。
