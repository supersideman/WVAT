# 毕设功能需求与技术方案（OV-Watch 手表板）

> 2026-10-19 · 硬件：OV-Watch（STM32F411CEU6，买成品或立创 SMT 贴片）
> 依据：[OV-Watch 评估报告](OV-Watch-毕设评估.md)、[FryPi 评估报告](FryPi-毕设方案评估.md) 及仓库/手册实证

## 一、结论

**功能表可行，但有 3 处必须改，否则 10 周做不完或在答辩现场翻车。**

| # | 你的需求 | 判定 | 说明 |
|---|---|---|---|
| 1 | 翻腕唤醒 | 🟡 **已有参考实现** | 板上 MPU6050 + RTC，作者已做（手册"翻腕亮屏"章）。直接抄=零贡献，必须做成"改进 + 实验" |
| 2 | 锁屏 + 滑动进主界面 | 🟡 部分现成 | 页面栈已存在（P29）；**滑动手势判定要自己写**，且受 CST816 软 IIC 采样率限制 |
| 3 | UI 自己设计 | ✅ 可行 | 但 512KB Flash 里 APP 占 390KB，**资源是奢侈品**（详见第四节） |
| 4 | 时间日期 | ✅ **现成** | RTC 已有，基本是"适配" |
| 5 | 设置功能 | ✅ **现成** | `DataSave.c` + EEPROM 已有 |
| 6 | 播放音乐 | ❌ **现有硬件做不了** | 见第二节，必须改成"播放控制" |
| 7 | 接入 AI（手表表达诉求 → 控制手机/电脑） | ⚠️ **方向对，架构要重画** | 手表无 WiFi、无麦 → 必须走"PC 网关"中转，见第三节 |

**最强的结论**：你这份需求真正值钱的不是"智能手表"，而是 7 号那条**双向意图通道**。建议把题目从"智能手表设计"重定位（见第五节），否则 1–5 号全是别人的现成功能，你的工作量撑不住答辩。

## 二、❌ 为什么"播放音乐"做不了

三条硬事实，都核对过：

1. **板子没有音频通路**：BSP 里只有 AHT21 / BL24C02 / EM7028 / IIC / KEY / KT6328 / LCD / LSM303DLH / MPU6050 / OWDG / POWER / SPL06 / TOUCH，**没有任何音频编解码、功放、喇叭、蜂鸣器驱动**；硬件文档也没提音频。
2. **蓝牙不能传音频**：KT6368A 是 **SPP 串口透传**模块（手册："有 SPP 功能，可以无线升级"），**不是 A2DP**——所以"连蓝牙耳机放歌"这条路也堵死。
3. **F411 软解 MP3 很勉强**：helix 一类解码器要额外占 Flash 与 RAM 缓冲，而 APP 已经吃掉 390KB/512KB。要本地出声还得飞线加 I2S DAC + 功放 + 喇叭。

**改法（推荐，且演示效果一样好）**：把"播放音乐"改成「**音乐播放控制**」——

> 手表屏上显示曲名/进度/播放状态，按键或触摸发指令经 SPP 给 PC，PC 端执行"播放/暂停/切歌/调音量"并把状态回传给手表。

这样做：不需要改硬件、和你第 7 条 AI 链路复用同一条通道、答辩现场"手表一按，电脑开始放歌"的观感甚至比手表自己响更好。

**若导师坚持要"本地出声"**：只能加 I2S DAC + 功放 + 小喇叭，飞线改板，工作量约 +1.5~2 周。**建议列为可选加分项，时间不够就砍**——这一条要提前跟导师说明。

## 三、⚠️ "接入 AI" 的架构要重画

你的原话是"通过手表给 AI 表达诉求，让 AI 来实现，比如控制手机、控制电脑"。这里有两个绕不过去的约束：

- **手表没有 WiFi**（只有 BLE-SPP 透传）→ 不能直连云端大模型 API（HTTPS/TLS）
- **手表没有麦克风**（板上无音频输入）→ "说话"这个输入方式要额外加硬件

### 推荐架构

```
┌─────────────┐   BLE SPP    ┌──────────────────┐   HTTPS   ┌────────────┐
│  OV-Watch   │ ──串口透传──> │  PC 端网关(Python)│ ────────> │ 云端大模型  │
│  (F411)     │ <──指令/状态──│  意图→动作执行器  │ <──────── │ (DeepSeek) │
└─────────────┘               └──────────────────┘           └────────────┘
   屏上显示意图/回复                  真正干活的地方
```

**为什么 PC 做网关是最优解**（三条依据）：

1. **作者已验证这条链路**：`Firmware/README.md` 里的 IAP 升级就是用"蓝牙配对成 Windows COM 口 + SecureCRT"完成的 → SPP→COM 的通路是现成的、被跑通过的。
2. **"控制电脑"和"播放音乐"在这里同时落地**：Python 端可以 `pyautogui` 控键鼠、`subprocess` 执行命令、控制播放器 → 一台 PC 就覆盖了你的两个执行类需求。
3. **Agent 逻辑放 PC 才好写**：意图解析、工具调用、结果回传、超时/失败兜底，全是 Python 的舒适区；放在 128KB 的 MCU 上是自找麻烦。

### 输入方式（关键取舍）

| 方案 | 评价 |
|---|---|
| 屏上打字 | ❌ 240×280 打中文体验灾难，且中文字库吃 Flash |
| 语音输入 | 🟡 要加 I2S 麦（板上没有，得飞线）→ **建议列为二期** |
| **图标/意图按钮 + 少量固定指令** | ✅ **推荐**：手表发"意图码"，PC 端 LLM 负责"意图 → 动作规划" |

推荐做法：手表上做几个意图入口（"我困了""放首歌""打开资料""锁屏电脑"），屏上显示 LLM 的短回复（用现有小字库就能显示）。**AI 的含金量不在"调 API"，在 PC 端 Agent 层的意图解析 + 工具调用 + 异常处理**——这一块全是你自己写的。

### 蓝牙链路的真相（已核实，来自作者手册「蓝牙串口通信协议」页）

**1）模块同时开两个蓝牙名**：`KT6368-SPP` 与 `KT6368-BLE`。作者明确要求**连 SPP、不要连 BLE**。调试工具作者也给了：资料收集页里的 `手机蓝牙串口助手.apk`。

**2）协议是纯 ASCII 文本行，前缀 `OV+`**，现成只有 4 条（实现在 `user_MessageSendTask.c`）：

```
OV                      // 测试
OV+VERSION              // 查看版本
OV+SEND                 // 查看传感器数据
OV+ST=20230629125555    // 同步时间
```

→ 好消息：**扩展指令极其简单**，你的 AI 意图直接设计成 `OV+AI=...` 就跟现有风格一致，论文里就是一节"通信协议扩展"，且**继承了你既有项目的经验又明显不同**（那是上报，这是下发指令）。

**3）手机能连，但不等于能用**。作者原话：

> "没有 APP 与手表进行操作的好吗, 需要可以自行写安卓 APP！"

也就是说：**Android 手机装个蓝牙串口助手就能调试**，但要做 AI 网关**必须自己写 App**——官方没有配套 App。iPhone 不支持 SPP，`KT6368-BLE` 那个实例没有公开文档，不建议碰。

**4）必须澄清一个概念**：蓝牙**不是让手表上网**。链路永远是「手表 —蓝牙→ 网关（PC/手机）— WiFi/4G → 云端」。答辩如果被问"你的手表怎么上网"，答"手表不上网，它把意图交给网关"。

### 电脑做网关 vs 手机做网关

| 维度 | 电脑（推荐） | Android 手机 |
|---|---|---|
| 现成通路 | ✅ 配对成 Windows COM 口，作者用这招做 IAP，已验证 | 需自写 App（或蓝牙串口助手仅能调试） |
| 调云端 API | ✅ Python 里 HTTPS 几行搞定 | 需在 App 内做 HTTP |
| 执行动作 | ✅ pyautogui 控键鼠、subprocess 跑命令、控播放器 | 受权限限制，复杂动作要无障碍服务 |
| 开发工作量 | **低，1–2 天能跑通** | **高，App 开发 1–2 周** |
| 答辩稳定性 | 自带笔记本就够 | 手机 + App + 网络三重依赖 |
| "控制手机"这个需求 | ❌ 管不到手机 | 🟡 网关就在被控设备上，反而顺 |

**结论**：主链路走**电脑**，把"控制电脑 + 音乐播放控制"一次做透；"控制手机"降级为论文里的方案讨论（并说明 iOS 无 SPP 这一限制，反而显得你想清楚了）。

若导师坚持要手机端：本科可行的捷径是 **MIT App Inventor**（有 BluetoothClient + Web 组件，能实现"收蓝牙文本 → 调 HTTP → 回传"），但 UI 粗糙、调试困难，**只在没有别的选择时用**。

### ⚠️ 必被问到的一句话，先准备好

> "这跟你之前那个 DeepSeek + STM32 火灾报警有什么区别？"

标准答案：**火灾报警是单向上报 + 阈值告警（数据流向上）；本课题是双向意图通道 + 动作执行 + 状态回执（控制流闭环），且终端是资源受限的穿戴设备，还要处理断连、时延与功耗的权衡。**

## 四、资源预算：先算账，再定 UI

- **Flash**：512KB，BootLoader 76KB + Flag 区，APP 已占 390KB → **余量不足 50KB**。作者用了 6 个字号的中文字库（Cuyuan 18/20/24/30/38/100），这已经很奢侈。
- **EEPROM**：板载 BL24C02 只有 **256 字节**（存设置够，存资源不行）。
- **没有 SPI Flash** → 图片/字库无处外挂，只能挤在 Flash 里。
- **RAM**：128KB，要分给 11 个线程栈 + LVGL 缓冲 + 协议缓冲。

**UI 设计的硬约束**：图标优先用 **LVGL 内置符号字体**，字号控制在 2–3 个，主题色用代码算而不是贴图。想贴图就得砍别的。**这张预算表本身就是论文里"资源受限设计"一节的实证数据。**

- ❌ 原题："基于 STM32 的智能手表设计" → 1–5 号功能全是别人的现成实现，评委一问就露
- ✅ 建议："**资源受限终端与云端智能体的双向意图通道设计与实现**"
  或"**基于 BLE-SPP 网关的穿戴终端智能交互系统**"

好处：主线从"UI 好看"（主观评分）变成"通信链路 + 意图解析 + 可靠性"（可量化、可写论文、更像自动化专业）。

## 八、风险清单（按疼的程度）

1. **答辩现场依赖 PC 在场**：蓝牙 COM 配对 + 网络 + LLM 额度，任一环节挂掉就演示不了。**必须全程录屏**，且提前在答辩用的那台电脑上实测。
2. **"现成功能"占比过高**：1–5 号都算"别人做过的"。对策——每一项都要有你的改进点和一组对比数据，不能只有"我做出来了"。
3. **Flash 余量不足 50KB**：UI 一铺开就爆。先定资源预算再画界面。
4. **CST816 触摸采样率**：作者自己就写过"由于 CST816 读取频率问题，绘制的触摸点与点之间距离会有一定距离" → 滑动会丢点，要做插值/方向判定容错。
5. **成品无备件**：弄坏了停摆两周，建议顺便问卖家能否买备用屏/电池。
6. **GPL-3.0 合规**：保留 LICENSE、README 写清 fork、论文里写明"基于 OV-Watch 二次开发，本文贡献为……"。

### 外壳模型实测尺寸（从仓库 STL 算的包围盒）

| 件 | 外形（mm） | 三角形数 |
|---|---|---|
| 后壳 `后壳零件.STL` | **37.20 × 56.20 × 10.75** | 5160 |
| 前壳 `前壳零件.STL` | **37.20 × 48.20 × 7.55** | 2056 |
| 按键 `按键零件.STL` | 6.55 × 9.40 × 7.20 | 1574 |

读得出的信息：
- 表壳主体约 **37.2 宽 × 48.2 长**；后壳 Y 向多出 **8mm**，那是**表带凸耳**（每侧约 4mm）→ 表带装在 Y 两端
- 三个文件都是标准二进制 STL、体积小（258/103/79 KB），**任何打印店都能直接接单**
- ⚠️ **总厚度不能简单相加**（两个 STL 是否共用同一原点，我无法从文件确认），装配厚度要放进切片软件对齐后才知道

**电池怎么选**：内腔容积算不出来（包围盒 ≠ 腔体），必须实测——把后壳 STL 丢进切片软件（Cura/PrusaSlicer）看内腔轮廓，或直接量打印件。锂电型号命名是 **厚度×宽度×长度（mm）**，比如 `402025` = 4×20×25mm，拿到腔体尺寸就能直接对型号。**别按任何估算数字承诺续航。**

### 装配红线（外壳到手前就该知道）

1. **屏是最脆的一环**：FPC 18P 插在板端 FPC 座里，没有外壳保护时最容易被扯断。**先用泡棉/亚克力做个"裸板测试台"跑通全部功能，再装壳。**
2. **锂电别买裸电芯**：要带保护板（PCM）的成品；引线极性别搞反（焊错直接烧 TPS63020）；别用烙铁长时间烫极耳；鼓包立即弃用。
3. **首次上电先串限流**：用万用表电流档或限流电源，确认静态电流正常、没短路再接电池。
4. 3D 打印件公差要磨：FDM 的卡扣/螺柱大概率偏紧，预留打磨和热熔铜螺母的时间（约半天）。

## 十、开工顺序（不等货也能马上干的部分）

判断：**外壳 / 表带 / 电池晚点弄是对的**，它们只影响"能不能戴"，不影响"功能能不能做通"。但有一件例外必须先解决——

### 供电：不用电池也能开发（已更正，依据作者「如何烧录」页）

板子**没有 USB 口**，正常供电路径是「3.7V 电池 → TPS63020 → 3V3」。但作者在手册「如何烧录」页给了明确的调试供电方法，原话：

> "如果焊接了排针，直接按照丝印写的网络插上 ST-LINK 即可，注意别插反接了即可。**电池端可以暂时不用**……**可以接 3.7V 锂电池或者接 5V Vcc**。"
>
> "如果没有焊接烧录口的排针（推荐，因为比较干净），则使用**烧录夹**，夹住烧录口插上 stlink 等下载即可。**烧录夹为 2.54mm 4pin**。"
>
> "小贴士：**调试时 3V3 处供电容易供电不稳，建议直接烧录夹夹住 BAT+ 端进行 5V 供电，充当电池**~"

三条路，作者的实际建议排序：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A 烧录夹夹 BAT+ 灌 5V**（作者推荐） | 2.54mm 4pin 烧录夹，从 BAT+ 端进 5V 充当电池 | 作者说 3V3 供电"容易不稳"，这条路最稳；**接上后要长按 KEY2 开机**（代码里是长按 Key2 使能供电） |
| B 烧录夹夹 SWD 口 | 夹 SWD 四针，ST-Link 直接供电 | 能跑，但作者提醒 3V3 处不稳；**别插反** |
| C 焊接排针 | 按丝印网络插 ST-LINK | 最干净是不焊排针，用烧录夹 |

**⚠️ 更正我之前的说法**：我上一轮写"绝对不要把 5V 灌到电池焊盘"是**不准确的**——作者明确写了 BAT+ 可以接 5V Vcc（TPS63020 输入上限 5.5V，5V 在范围内）。但保险起见仍建议：**串限流、别同时插 5V 充电口、先测静态电流再长时间跑。**

**对计划的影响**：**电池不再是阻塞项**，阶段 1 完全可以靠下载器 / BAT+ 5V 跑起来，外壳和电池照样可以晚买。但两件事别忘：
1. **要做功耗 / 续航 / 翻腕唤醒的能耗实验时，仍必须有真电池 + µA 级电流表**——这部分数据靠 5V 实验电源做不出来（电源路径根本不是电池）。
2. **长时间跑全功能时优先用 BAT+ 5V 那条路**，否则 3V3 供电不稳会导致**闪屏、重启、蓝牙掉线**，很容易被误判成软件 bug 白查两天。

### 调试 APP 的两个必改项（不烧 BootLoader 时）

作者在「如何烧录」页写了：只调试 APP 不烧 BootLoader 时，
- Keil 工程 **ROM 地址设为 `0x08000000`**
- `main.c` 里地址偏移改为 `0x00000000U`，即 `SCB->VTOR = 0x00000000U;`

功能调完要回到 IAP 流程时，**偏移改回 `0x0800C000`**（= 48KB，Boot 区大小），再按 OTA 步骤发 `.bin`。这两处忘改，会出现"烧进去不跑"的经典困惑。

### 阶段 0：现在就能做，零等待（这两天就干这个）

1. **LVGL 仿真里先把 UI 画出来** ← 最优先。仓库里有 `lv_sim_vscode_win`，`HW_USE_HARDWARE=0` 就能在 PC 上跑裸 UI。**UI 是耗时最多、又最不依赖硬件的一环**，先在仿真里做，板子到了直接拷进去。
2. **设计协议帧格式**：`OV+AI=` 指令集、字段编码、校验、超时重传。这是电脑网关与手表端唯一必须对齐的接口，定错了后面全返工。
3. **PC 网关骨架**：串口读行 → 调云端 LLM → 执行动作 → 回写状态。**没有手表也能测**——用虚拟串口或手写模拟数据喂它。

### 阶段 1：到货后 1–2 天（硬件链）

点灯 → 屏亮 → 触摸有反应 → 跑通原厂固件（Boot + APP）→ 改一屏 UI 并烧进去。**这一步过了才算真正开始。**

### 阶段 2：W3–W5（联动）

蓝牙配对成 Windows COM 口 → 手表的意图按钮发 `OV+AI=...` → PC 网关执行 → 屏幕显示回复。**这是你答辩演示的核心 30 秒。**

### 排序原则

把活切成两堆：**不依赖硬件的（阶段 0）现在就干，依赖硬件的集中在到货后两周**。这样缺件完全不拖进度。

## 十一、输入方式：直觉对，但结论要反一下

**你的直觉是对的——手表打字不靠谱。但结论不该是"那就改用语音"，而是"根本不该让用户表达自由文本"。**

### 为什么打字确实不行（不只是"感觉"）

- 240×280 的屏，一行 8–10 个汉字，3 行就满；软键盘一弹，剩下半屏
- CST816 是**软 IIC 轮询**，作者自己写过"由于 CST816 读取频率问题，绘制的触摸点与点之间距离会有一定距离"→ 手写/滑动都会丢点
- 九宫格拼音要词库 + 中文字库，而 **APP 的 Flash 余量不到 50KB**

### 为什么语音在现有板子上更难

先看硬件：BSP 的 13 个模块里**没有任何音频相关驱动**，硬件文档也没提麦克风；从手册描述看，板上只有 **SWD 4pin 的焊盘位**（可焊排针），**没有整排 IO 引出**——想加 I2S 麦，基本只能从 QFN48 引脚飞线。（此点依手册描述推断，需对照 `Hardware/SCH_Core_2024-05-26.pdf` 确认。）

就算接上了麦，还有第二道坎——**音频要变成文字**：

| 路线 | 做法 | 代价 |
|---|---|---|
| **端侧关键词唤醒（KWS）** | 本地小 CNN 识别 5–10 个固定词 | ✅ 可行（~1–3 万参数）；但**只认固定词，不能自由说话** |
| **自由说话 → 云端 ASR** | 音频流经蓝牙送 PC → ASR → 文本 → LLM | ⚠️ 8kHz/16bit 单声道 = **16KB/s**，而蓝牙透传实际吞吐通常只有几 KB/s～十几 KB/s → **音频流会挤占带宽，心跳和指令跟着延迟丢包**；必须压缩（ADPCM 减半）或只传 MFCC 特征 |

### 五种输入方式，摊开比较

| 方案 | 表达力 | 实现代价 | 风险 | 建议 |
|---|---|---|---|---|
| **意图图标网格（9 宫格）** | 低，但覆盖 80% 场景 | **低** | 低 | ✅ **主力** |
| 手势（翻腕/双击/摇一摇） | 很低 | 低 | 中（触摸丢点） | ✅ 辅助 |
| 屏上文本输入 | 中 | 中 | **高**（屏小+Flash 紧） | 🟡 加分项，别当主力 |
| 语音关键词（本地 KWS） | 低-中（固定词表） | 中高（加麦+训练） | 中 | 🟡 二期，有麦再说 |
| 语音自由说话（云端 ASR） | 高 | **高**（加麦+音频流+ASR） | **高** | ❌ 现有板子不推荐 |

### 所以正确的交互设计是

> **手表上让用户"选"，而不是"打"或"说"。** 把意图收敛到有限集合，用图形表达——这既符合硬件约束，也符合手表"抬腕 3 秒完成"的使用场景。

具体做法：抬腕亮屏 → 主界面下方一排意图图标（放歌 / 我困了 / 音量 / 资料 / 状态）→ 单击即发。**"自由文本"降级为一个隐藏页**，只在想演示时才用。

### 补充：原理图核查结果（从仓库 `Hardware/SCH_Core/Back_2024-05-26.pdf` 提取）

我把两张原理图 PDF 的网络名提取出来核对了一遍，结论是**这块板子加麦克风基本不可行**：

**1）没有可用的扩展 IO**

- MCU 是 UFQFPN48，**全部 GPIO 共 34 个**（PA0–PA15、PB0–PB10 + PB12–PB15、PC13–PC15；PB11 和 PC0–PC12 这个封装根本没有）
- 已占用的网络约 **29 个**：`LCD_MOSI/CLK/DC/CS/RST/BLK`、`TP_SCL/SDA/RST/INT`、`SENSOR_SCL/SDA/INT`、`PROM_SCL/SDA`、`KEY1`、`WAKE`、`WDI`、`#WDOG_EN`、`UID_SEL`、`LED_EN`、`POWER_EN`、`CHARG`、`BAT_DET`、`USART1_TX/RX`、`BLE_EN`、`SWDIO/SWCLK`、`OSC32IN/OUT`
- **剩 ≤5 个，而且没有引到任何排针阵列上**——Core 板上只有 SWD 4 针焊盘位和几个专用小连接器

**2）板间连接只有 9 针**：Core↔Back 靠 H5/H2（9P）互联，只走 `SDA/SCL/3V3/BLE_EN/BLE_RX/BLE_TX/LED_EN/MPU6050_INT/GND`。**扩展性≈0**。

**3）要接麦只能从 QFN48 引脚飞线**（0.5mm 间距），成功率低，容易报废整块板。

> 方法说明：PDF 文本层只能拿到网络名清单，拿不到"哪个脚接哪个网络"的空间对应关系（那在图形里）。以上占用数按网络名 + 封装引脚数推算，**如需精确到脚，要打开 PDF 逐脚核对**。

**顺带查到的三个有用结论：**

| 发现 | 影响 |
|---|---|
| **32.768kHz LSE 晶振确实焊了**（X1 + 7pF 电容，PC14/PC15） | ✅ 我之前的担心解除：RTC、低功耗定时唤醒都能做 |
| **没有 25MHz HSE 晶振**（全表只有那一个晶振） | 主频走 HSI + PLL；这也解释了板子为什么没有 USB 口。⚠️ 副作用是 **I2S 采样时钟精度差**，做音频采集/播放要留意 |
| Back 板传感器确认：MPU6050、SPL06-001、LSM303DLHC、AHT21、EM7028，共用一条 IIC | 与手册一致；BLE 模块也在 Back 板 |

### ✅ 那么"语音"怎么办：用 PC 的麦克风

不改硬件也能实现语音，办法是**把麦克风放在网关那端**：

```
手表按"语音"按钮 → PC 端开始录音（PC 自带麦）
                → ASR 转文字 → LLM 理解 → 回传结果 → 手表显示
```

- **手表端零硬件改动**，只发一条 `OV+AI=<id>,A07`（VOICE）
- 体验上是"对着笔记本说话"，而不是"对着手表说话"——但对"我困了""放首歌"这类场景完全够用
- 论文里可以正当地写成**"端云协同：终端不承担语音采集，由网关侧完成 ASR"**，这是一个说得通的架构选择，不是妥协
- 代价：延迟明显变长（2–5s），**必须做"处理中"动画**，且要防用户重复触发

**建议**：把语音做成二期的"锦上添花"，主力仍是图标按钮。真要"对着手表说话"，只能换 FryPi 或 F411+自画底板。

### 决策树

```
"对着手表说话" 是刚需吗？
├─ 是，要自由说话  → 必须换硬件（FryPi 2×26P 排针 / F411 核心板+自画底板），
│                    并在论文里把"端侧 KWS 或音频流压缩"写成技术路线
└─ 否，只要"酷一点"→ 现有 OV-Watch 板就够：
                     用一个"关键词唤醒"当二期加分项（说"助手"→ 亮屏弹意图网格），
                     主力仍是图标按钮
```

**一句实在话**：答辩演示里，"说一句『助手』→ 屏幕亮起 → 点一下『我困了』→ 电脑立刻锁屏"这个效果，**和"对着手表说一整句话"相比，观感差距远小于工程代价差距**。省下来的两周足够你把协议、网关和实验数据做扎实。
