# 项目定位与能力边界（开题一页纸）

> 2026-10-19 · 面向本科毕设的选题定位 · 硬件底座：FryPi / F411（语音需要 I2S） + 后期做腕带形态

## 一、一句话定位

**"个人 AI 便携控制终端"**——一个可随身携带的语音代理入口：按住说话，云端 AI 理解意图并调度电脑执行，结果回传显示。

> 一句话讲给老师听：**"它不是智能手表，是戴在手上的 AI 遥控器。"**

建议给它一个正式名字（论文封面要用），例如：
- 中文：随身语音代理终端 / 个人 AI 控制助手
- 英文全称：**Wearable Voice Agent Terminal（WVAT）**

**这个定位最大的价值**：把项目的主线从"复刻一块智能手表"（别人的现成功能）**迁移到"端—代理—云 三端协同的语音控制链路"**（你自己的设计）。答辩时，"哪部分是你做的"这个问题就有干净利落的答案。

## 二、三端分工（系统架构章的主干）

| 角色 | 承担 | 不承担 |
|---|---|---|
| **终端**（手表） | 语音采集、意图触发、状态显示、本地降级指令 | 不做语义理解、不联网、不执行 |
| **代理**（PC 网关） | ASR、意图解析、动作白名单调度、执行、**语音播报反馈** | 不做界面渲染 |
| **认知**（云端 LLM） | 模糊语义 → 结构化动作映射 | **绝不直接执行任何操作** |

## 三、能力边界（三层，明确"做什么"和"不做什么"）

| 层级 | 内容 | 做到什么程度 |
|---|---|---|
| **L1 本机控制** | 锁屏 / 静音 / 播放·暂停·切歌 / 音量 / 打开程序或文件 | ✅ **做扎实**，这是演示主力 |
| **L2 信息查询** | 时间、天气、日程、待办（需外部 API） | ✅ 做，但要标注"依赖第三方 API" |
| **L3 模糊意图组合** | "我有点困了"→ 锁屏+静音+降亮度 | 🟡 **只做 3–5 个 demo 场景**，别贪 |
| **不做** | 控制真实物理世界（灯/车/家电）、控制手机 App、任意 shell 命令 | ❌ 明确写进"未来工作" |

**为什么必须划这条线**：老师说"有逻辑有内容"，怕的正是"什么都说能做，结果什么都只做了个演示壳"。**边界写清楚反而是加分项。**

## 四、★ 一个容易被忽略的体验缺口：反馈

**手表没有喇叭，也没有振动马达**（BSP 里 13 个模块无音频、无马达）。这意味着用户说完话后，**没有任何物理反馈能告诉他"我听见了/正在办/办完了"**。

而你的使用场景是"边干别的事"——**人不会一直盯着手表看**。所以反馈必须这样设计：

```
按下列录音 → 手表屏幕显示"录音中"（视觉反馈）
          → PC 端播报一声"嘀"（听觉反馈，用电脑的喇叭！）
          → 执行完毕 → PC 用 TTS 说"已锁屏并静音" + 手表屏显同样文字
```

**把 TTS 放在 PC 端，是这个设计能成立的关键**：终端负责输入与显示，代理负责执行与发声。这条"反馈闭环"完全可以写成论文里的一节人机交互设计。

## 五、一次完整交互（答辩就演这个）

```
1. 用户（手在别处）按下手表侧键        → 屏幕："🎤 录音中"
2. 说"帮我放首歌"（2 秒）              → 松开/再按结束
3. 手表经蓝牙发出压缩音频               → 屏幕："识别中…"
4. PC 端 ASR → 文本                     → 屏幕："思考中…"
5. LLM → {"action":"MUSIC_PLAY"}        → 屏幕："执行中…"
6. PC 执行 + TTS 播报"正在播放"         → 屏幕："已开始播放"
```

**四段状态机**（录音中/识别中/思考中/执行中）是必须做的：用户觉得"卡"，往往不是真的慢，而是没有反馈。

## 六、可量化的指标（论文的数据来源）

| 指标 | 怎么测 | 为什么重要 |
|---|---|---|
| 语音识别准确率 | 安静/嘈杂两档，各 50 句 | 决定"趁手程度" |
| 端到端时延 | 按下到执行完成的毫秒数 | 4–9s 是现实区间，要如实报告 |
| 意图执行成功率 | 100 次触发里正确执行的占比 | 系统的可信度 |
| **断网降级可用率** | 断网后 L1 指令仍能执行的比例 | 你的独特卖点 |
| 功耗/续航 | µA 级电流表 + 电池 | 后期形态阶段再做 |

## 七、与既有项目的区别（必被问，先备好）

| | DeepSeek + STM32 火灾报警 | 本项目 |
|---|---|---|
| 数据流向 | 单向上报（传感器 → 云端） | **双向**（意图上行 + 结果下行） |
| 交互方式 | 自动触发，无人参与 | **人主动发起的语音交互** |
| 终端角色 | 数据采集器 | **便携人机接口** |
| 技术难点 | 阈值判断、告警通路 | **语音链路、意图解析、反馈闭环、时延控制** |

## 八、风险提醒（愿景越大越要防）

1. **语音准确率是这个产品的命门**：日常环境有噪声、口音、说话随意，识别率会明显下降。所以**指令式（关键词本地匹配）必须保底**，不能全靠自由语音。
2. **"边干别的边用"意味着不能看屏幕**：所以 PC 端播报反馈是刚需，不是锦上添花。
3. **愿景膨胀**：L3 只做 3–5 个场景。"能控制一切"这句话一句都别说。
4. **技术配比失衡**：这个项目的工作量大头在 **PC 端代理 + 语音链路调优**（约 50%），手表端 UI 约 30%，语音调参约 20%。别把时间都花在画界面上。
